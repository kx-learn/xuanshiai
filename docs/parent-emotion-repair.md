## 实现与边界

父母授权采用随机邀请、成年子女明确确认、一次一子女关系、逐次校验、撤销和到期失效。代理业务复用既有用户资料、喜欢、申请、匹配、聊天、屏蔽与举报服务；新增表只保存授权、偏好和代理审计。此方案保持用户与聊天数据的唯一来源，减少多套“父母数据”的同步风险。

MBTI 会话保存题目、极性、量表、计分方向、维度与结果文案快照。旧列表快照只在确认为 `mbti-core@2 / mbti-result-copy@2` 时使用不可变归档；未知旧版本明确拒绝，避免套用当前文案。MySQL JSON对象排序不得决定MBTI字母顺序，始终按EI、SN、TF、JP计算。正数半分采用整数四舍五入，与前端Math.round一致。完成结果和来源模型同时接受camelCase与既有snake_case存储字段。

真实资料编辑页只展示已确认的MBTI来源，选择与确认在情感实验室完成。普通资料PATCH不允许改变MBTI；旧客户端原样回传当前值可兼容，但不能借此更改类型或伪造来源。资料或偏好加载失败保留错误态，不以固定演示人物覆盖真实资料。

## 增量数据库迁移

仅执行 [20260906_parent_delegation.sql](../migrations/20260906_parent_delegation.sql)，包含三个 `CREATE TABLE IF NOT EXISTS`：

| 表 | 目的 | 默认状态 |
| --- | --- | --- |
| parent_relationship | 父母与单子女关系、授权、邀请码哈希及过期时间 | 待授权；不生成虚构子女 |
| parent_preferences | 当前账号的页内提醒及照片许可 | 提醒开启、照片许可关闭 |
| parent_action_event | 操作人、父母、子女、操作类型、候选和时间 | 不记录令牌、邀请码、聊天正文或联系方式 |

新表直接声明六个用户外键和关系状态CHECK，要求MySQL 8.0.16及以上；用户采用既有软删除策略，外键不级联删除审计。已有库不会修改或清空用户、申请、消息、MBTI数据。重复执行DDL安全，但IF NOT EXISTS不会自动升级曾手工创建的同名试验表，遇到同名表须先对照SHOW CREATE TABLE。

迁移流程：对目标库做常规备份；确认连接的是目标环境；执行SQL；检查三张表及六个外键；部署后端；完成测试账号的邀请→子女确认→撤销验收；再发布前端。应用的完整初始化器也包含这些表，但本次增量发布无需对已有库运行完整初始化。

回退时停止新父母入口或回退前端，并保留新增关系与审计表。不要DROP表来“恢复现场”。已写入对象式快照的MBTI会话需要保留本次兼容读取器；不能直接回退到只接受列表快照的旧服务，否则旧代码无法读取新会话。旧代码问题应通过保留读取兼容性的修正版处理，不能重算或覆盖用户已完成结果。
